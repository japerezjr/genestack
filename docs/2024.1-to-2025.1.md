# Upgrading Genestack from OpenStack 2024.1 (Caracal) to 2025.1 (Epoxy)

This guide provides comprehensive instructions for upgrading a Genestack deployment from OpenStack 2024.1/2024.2 (Caracal) to 2025.1 (Epoxy). Genestack leverages OpenStack-Helm charts for deployment and management, making upgrades primarily a matter of updating the underlying charts and configurations via Git and Helm.

OpenStack 2025.1 (Epoxy) is a Skip Level Upgrade Release Process (SLURP) release, which supports direct upgrades from the previous SLURP release (Caracal), skipping the intermediate 2024.2 (Dalmatian) release if desired. This simplifies the upgrade path for stable environments.

## Overview

The upgrade process consists of four main phases:

1. **Pre-upgrade validation** - Verify system health and readiness
2. **Chart and configuration updates** - Update helm chart versions and configurations
3. **Upgrade execution** - Apply updates in dependency order with health monitoring
4. **Post-upgrade verification** - Validate service functionality and performance

This guide covers both automated upgrade using the `openstack-upgrade` tool and manual upgrade procedures.

## Expected Timeline

Upgrade duration varies based on deployment size and complexity:

- **Small deployment** (3 nodes, core services only): 30-60 minutes
- **Medium deployment** (5-10 nodes, core + some optional services): 1-2 hours
- **Large deployment** (10+ nodes, all services): 2-4 hours

**Downtime expectations:**
- Infrastructure services (memcached, mariadb, rabbitmq): No downtime expected
- Core services (keystone, nova, neutron, etc.): 5-15 minutes API downtime per service
- Optional services: Can be upgraded independently with minimal impact
- **Total expected downtime for core services: 30-60 minutes**

## Prerequisites

### Required Preparations

1. **Full System Backup**
   - Complete database backups for all OpenStack services (MariaDB/PostgreSQL)
   - Backup of helm-chart-versions.yaml
   - Backup of all configuration overrides in base-helm-configs/
   - Verify backups are recent (within 24 hours) and restorable
   - Store backups in a secure location outside the cluster

2. **System Health Verification**
   - All OpenStack services must be healthy and operational
   - All Kubernetes pods in Running state
   - All OpenStack API endpoints responding correctly
   - No active migrations or database sync operations
   - No pending or failed jobs in the openstack namespace

3. **Resource Validation**
   - Sufficient cluster resources available (CPU, memory, storage)
   - Adequate disk space for backups (minimum 50GB recommended)
   - Network connectivity stable and verified
   - No resource exhaustion warnings

4. **Maintenance Window**
   - Schedule maintenance window during low-usage period
   - Notify users of planned downtime (recommend 2x expected duration)
   - Prepare communication plan for status updates
   - Have rollback plan ready and tested

5. **Access and Permissions**
   - Administrative access to Kubernetes cluster
   - OpenStack admin credentials
   - Access to helm chart repositories
   - SSH access to management nodes

6. **Documentation Review**
   - Review this upgrade guide completely
   - Review breaking changes documentation
   - Review rollback procedures
   - Familiarize with troubleshooting section

### Breaking Changes in Epoxy

Be aware of these critical breaking changes:

1. **oslo.messaging Configuration**
   - `heartbeat_in_pthread` option deprecated (remove from configs)
   - `kombu_ssl_*` options removed (use non-prefixed versions)
   - Several options moved from `[DEFAULT]` to `[oslo_messaging_rabbit]`
   - AMQP1 driver removed

2. **Ironic**
   - PostgreSQL support removed - only MySQL/MariaDB supported
   - If using PostgreSQL, migrate to MariaDB before upgrade

3. **Neutron**
   - Linux Bridge mechanism driver removed
   - If using Linux Bridge, migrate to OVS or OVN before upgrade

4. **Python Version**
   - Minimum Python 3.9 required (Python 3.8 support removed)

See the [Breaking Changes](#breaking-changes) section for complete details.


## Upgrade Methods

Genestack provides two methods for upgrading to Epoxy:

### Method 1: Automated Upgrade (Recommended)

The automated upgrade tool provides a comprehensive, validated upgrade path with built-in safety checks, rollback capability, and detailed reporting.

**Advantages:**
- Automated pre-upgrade validation
- Dependency-aware service ordering
- Built-in health monitoring
- Automatic rollback on failure
- Comprehensive logging and reporting
- Dry-run mode for testing

**See:** [Automated Upgrade Procedure](#automated-upgrade-procedure)

### Method 2: Manual Upgrade

Manual upgrade provides more control and visibility into each step but requires careful attention to service dependencies and validation.

**Advantages:**
- Full control over each step
- Ability to pause and inspect at any point
- Useful for troubleshooting specific issues
- No additional tooling required

**See:** [Manual Upgrade Procedure](#manual-upgrade-procedure)

## Automated Upgrade Procedure

The automated upgrade tool is located in `upgrade-tools/` and provides a comprehensive CLI interface for all upgrade operations.

### Step 1: Install Upgrade Tool

```bash
cd /opt/genestack/upgrade-tools

# Create virtual environment
python3 -m venv venv
source venv/bin/activate

# Install dependencies
pip install -r requirements.txt
```

### Step 2: Configure Upgrade

Review and customize the upgrade configuration:

```bash
# Edit configuration file
vi config/upgrade-config.yaml
```

Key configuration options:
- `source_release`: Current OpenStack version (2024.1 or 2024.2)
- `target_release`: Target version (2025.1)
- `namespace`: Kubernetes namespace (default: openstack)
- `skip_optional_services`: Set to true to upgrade only core services
- `timeout_per_service`: Timeout in seconds per service (default: 600)

### Step 3: Run Pre-Upgrade Validation

Validate system readiness before starting the upgrade:

```bash
./openstack-upgrade --validate-only
```

This checks:
- All pods are in Running state
- All OpenStack API endpoints are responding
- Database backups exist and are recent
- Sufficient cluster resources available
- No active migrations or jobs running

**If validation fails, fix all issues before proceeding.**

### Step 4: Perform Dry-Run

Test the upgrade without making changes:

```bash
./openstack-upgrade --dry-run
```

Review the output to understand:
- Which chart versions will be updated
- Which configurations will be modified
- Service upgrade order
- Estimated duration

### Step 5: Execute Upgrade

Run the full upgrade:

```bash
# Full upgrade with all services
./openstack-upgrade

# Or upgrade only core services
./openstack-upgrade --skip-optional

# Or upgrade specific services
./openstack-upgrade --services keystone glance nova neutron
```

The tool will:
1. Create automatic backups
2. Update chart versions
3. Validate configurations
4. Upgrade services in dependency order
5. Monitor health after each service
6. Generate upgrade report

**Monitor the output for any errors or warnings.**

### Step 6: Verify Upgrade

After upgrade completes, verify all services:

```bash
# Check pod status
kubectl get pods --all-namespaces

# Verify OpenStack services
openstack endpoint list
openstack compute service list
openstack network agent list
openstack volume service list

# Test basic operations
openstack server list
openstack network list
openstack volume list
```

### Step 7: Review Upgrade Report

The upgrade tool generates a comprehensive report:

```bash
# View report (if saved to file)
cat upgrade-report.txt

# Or check logs
tail -f upgrade-tools/upgrade.log
```

### Rollback (If Needed)

If the upgrade fails or issues are discovered:

```bash
# Automatic rollback
./openstack-upgrade --rollback
```

The tool will:
1. Restore previous chart versions
2. Restore previous configurations
3. Reapply previous helm releases
4. Verify service health

See [Rollback Procedures](#rollback-procedures) for details.

## Manual Upgrade Procedure

### Step 1: Create Backups

```bash
# Backup helm chart versions
cp helm-chart-versions.yaml helm-chart-versions.yaml.backup

# Backup override configurations
tar -czf base-helm-configs-backup.tar.gz base-helm-configs/

# Backup databases (example for MariaDB)
kubectl exec -n openstack mariadb-server-0 -- \
  mysqldump --all-databases > openstack-databases-backup.sql
```

### Step 2: Update Git Repository

Navigate to the Genestack directory and update:

```bash
cd /opt/genestack

# Fetch latest changes
git fetch origin

# View available tags
git tag | grep 2025.1

# Checkout Epoxy release
git checkout <Latest-Epoxy-Release-Tag>
```

### Step 3: Update Chart Versions

If no release tag is available, manually update helm-chart-versions.yaml:

```yaml
# Update OpenStack service versions from 2024.1/2024.2 to 2025.1
# Example:
keystone: 0.3.0  # Update to Epoxy version
glance: 0.3.0    # Update to Epoxy version
nova: 0.3.0      # Update to Epoxy version
# ... etc
```

### Step 4: Update Override Configurations

Update image tags in override files (base-helm-configs/*/):

```yaml
# Example: base-helm-configs/keystone/keystone-helm-overrides.yaml
images:
  tags:
    keystone_api: ghcr.io/aedan/genestack-images/keystone:2025.1-<build>
    keystone_db_sync: ghcr.io/aedan/genestack-images/keystone:2025.1-<build>
    # ... update all image tags to 2025.1
```

**Remove deprecated oslo.messaging options:**

```yaml
# Remove these from all service configs:
conf:
  oslo_messaging_rabbit:
    # Remove: heartbeat_in_pthread
    # Remove: kombu_ssl_* (use non-prefixed versions)
```

### Step 5: Clean Up Existing Jobs

Clean up Nova jobs to avoid conflicts:

```bash
kubectl --namespace openstack delete jobs \
  $(kubectl --namespace openstack get jobs --no-headers \
  -o custom-columns=":metadata.name" | grep nova)
```

### Step 6: Upgrade Services

Upgrade services in dependency order:

**Infrastructure Services (no downtime expected):**

```bash
# Memcached
helm upgrade --install memcached ./base-kustomize/memcached \
  --namespace openstack --timeout 10m --wait

# MariaDB Operator (if version changed)
helm upgrade --install mariadb-operator ./base-kustomize/mariadb-operator \
  --namespace openstack --timeout 10m --wait

# RabbitMQ (if version changed)
helm upgrade --install rabbitmq ./base-kustomize/rabbitmq-cluster \
  --namespace openstack --timeout 10m --wait
```

**Core Services (brief API downtime):**

```bash
# Keystone (Identity)
/opt/genestack/bin/install-keystone.sh

# Glance (Image)
/opt/genestack/bin/install-glance.sh

# Placement
/opt/genestack/bin/install-placement.sh

# Cinder (Volume)
/opt/genestack/bin/install-cinder.sh

# Neutron (Network)
/opt/genestack/bin/install-neutron.sh

# Nova (Compute)
/opt/genestack/bin/install-nova.sh

# Horizon (Dashboard)
/opt/genestack/bin/install-horizon.sh
```

**Optional Services (as needed):**

```bash
# Octavia (Load Balancer)
/opt/genestack/bin/install-octavia.sh

# Heat (Orchestration)
/opt/genestack/bin/install-heat.sh

# Magnum (Container Orchestration)
/opt/genestack/bin/install-magnum.sh

# ... other optional services
```

**Monitor each service after upgrade:**

```bash
# Watch pod status
kubectl get pods -n openstack -w

# Check service health
openstack compute service list
openstack network agent list
```

### Step 7: Post-Upgrade Verification


   - Check pod status:

     ```bash
     kubectl get pods --all-namespaces
     ```

   - Run OpenStack health checks:

     ```bash
     openstack endpoint list
     openstack compute service list
     openstack network agent list
     openstack volume service list
     ```

   - Test key functionalities:

     ```bash
     # Create test instance
     openstack server create --flavor m1.small --image cirros \
       --network private test-instance
     
     # Create test network
     openstack network create test-network
     
     # Create test volume
     openstack volume create --size 1 test-volume
     
     # Clean up test resources
     openstack server delete test-instance
     openstack network delete test-network
     openstack volume delete test-volume
     ```

   - Monitor logs for errors:

     ```bash
     # Check recent logs for all services
     kubectl logs -n openstack -l application=keystone --tail=100
     kubectl logs -n openstack -l application=nova --tail=100
     kubectl logs -n openstack -l application=neutron --tail=100
     ```

## Breaking Changes

### oslo.messaging Configuration Changes

**Issue:** Several oslo.messaging options have been deprecated or removed in Epoxy.

**Affected Services:** All services using RabbitMQ (nova, neutron, cinder, etc.)

**Changes Required:**

1. Remove `heartbeat_in_pthread` option:
   ```yaml
   # REMOVE this from all service configs:
   conf:
     oslo_messaging_rabbit:
       heartbeat_in_pthread: false  # REMOVE THIS LINE
   ```

2. Update SSL options:
   ```yaml
   # OLD (Caracal):
   conf:
     oslo_messaging_rabbit:
       kombu_ssl_ca_certs: /path/to/ca.pem
       kombu_ssl_certfile: /path/to/cert.pem
       kombu_ssl_keyfile: /path/to/key.pem
   
   # NEW (Epoxy):
   conf:
     oslo_messaging_rabbit:
       ssl_ca_file: /path/to/ca.pem
       ssl_cert_file: /path/to/cert.pem
       ssl_key_file: /path/to/key.pem
   ```

3. Move options from [DEFAULT] to [oslo_messaging_rabbit]:
   ```yaml
   # OLD (Caracal):
   conf:
     DEFAULT:
       rpc_response_timeout: 60
   
   # NEW (Epoxy):
   conf:
     oslo_messaging_rabbit:
       rpc_response_timeout: 60
   ```

**Impact:** Services will fail to start if deprecated options are present.

**Mitigation:** Update all override files before upgrade.

### Ironic PostgreSQL Support Removed

**Issue:** Ironic no longer supports PostgreSQL databases.

**Affected Services:** Ironic (bare metal provisioning)

**Changes Required:**
- If using PostgreSQL for Ironic, migrate to MySQL/MariaDB before upgrade
- Update database connection strings in ironic-helm-overrides.yaml

**Impact:** Ironic will fail to start if PostgreSQL is configured.

**Mitigation:** Complete database migration before starting upgrade.

### Neutron Linux Bridge Driver Removed

**Issue:** Linux Bridge mechanism driver has been removed from Neutron.

**Affected Services:** Neutron (networking)

**Changes Required:**
- If using Linux Bridge, migrate to Open vSwitch (OVS) or OVN before upgrade
- Update neutron-helm-overrides.yaml to use OVS or OVN

**Impact:** Networking will fail if Linux Bridge is configured.

**Mitigation:** Complete network driver migration before starting upgrade.

### Python 3.8 Support Removed

**Issue:** Minimum Python version is now 3.9.

**Affected Services:** All OpenStack services

**Changes Required:**
- Ensure all nodes have Python 3.9 or later
- Update any custom scripts or tools

**Impact:** Services may fail to start on Python 3.8.

**Mitigation:** Upgrade Python on all nodes before OpenStack upgrade.

## Rollback Procedures

If the upgrade fails or critical issues are discovered, you can rollback to the previous version.

### Automated Rollback

Using the upgrade tool:

```bash
cd /opt/genestack/upgrade-tools
source venv/bin/activate

# Initiate rollback
./openstack-upgrade --rollback
```

The tool will:
1. Restore previous helm-chart-versions.yaml
2. Restore previous override configurations
3. Reapply previous helm chart versions
4. Verify service health

### Manual Rollback

If automated rollback fails or is not available:

1. **Restore Configuration Files:**

   ```bash
   # Restore helm chart versions
   cp helm-chart-versions.yaml.backup helm-chart-versions.yaml
   
   # Restore override configurations
   tar -xzf base-helm-configs-backup.tar.gz
   ```

2. **Rollback Services:**

   ```bash
   # Rollback each service using helm
   helm rollback keystone -n openstack
   helm rollback glance -n openstack
   helm rollback nova -n openstack
   helm rollback neutron -n openstack
   # ... etc
   ```

3. **Restore Databases (if needed):**

   ```bash
   # Only if database schema changes occurred
   kubectl exec -n openstack mariadb-server-0 -- \
     mysql < openstack-databases-backup.sql
   ```

4. **Verify Rollback:**

   ```bash
   # Check pod status
   kubectl get pods -n openstack
   
   # Verify services
   openstack compute service list
   openstack network agent list
   openstack volume service list
   ```

### Rollback Decision Criteria

Consider rollback if:
- Multiple services fail to upgrade
- Critical services (keystone, nova, neutron) are non-functional
- Data corruption is detected
- Performance degradation is severe
- Security vulnerabilities are introduced

Do NOT rollback if:
- Only optional services failed (can be fixed independently)
- Minor configuration issues (can be fixed in place)
- Cosmetic issues in Horizon dashboard
- Non-critical warnings in logs

## Troubleshooting

### Common Issues and Solutions

#### Issue: Pods Stuck in Pending State

**Symptoms:**
```bash
kubectl get pods -n openstack
# Shows pods in Pending state
```

**Causes:**
- Insufficient cluster resources
- Node affinity/anti-affinity conflicts
- Storage provisioning issues

**Solutions:**
```bash
# Check pod events
kubectl describe pod <pod-name> -n openstack

# Check node resources
kubectl top nodes

# Check storage classes
kubectl get storageclass

# If resource issue, scale down non-critical services temporarily
kubectl scale deployment <deployment> --replicas=0 -n openstack
```

#### Issue: Database Migration Failures

**Symptoms:**
```bash
kubectl logs <service>-db-sync-xxx -n openstack
# Shows database migration errors
```

**Causes:**
- Database connection issues
- Schema conflicts
- Insufficient database permissions

**Solutions:**
```bash
# Check database connectivity
kubectl exec -n openstack mariadb-server-0 -- mysql -e "SHOW DATABASES;"

# Check database user permissions
kubectl exec -n openstack mariadb-server-0 -- \
  mysql -e "SHOW GRANTS FOR 'keystone'@'%';"

# Manually run db-sync (example for keystone)
kubectl exec -n openstack keystone-api-xxx -- \
  keystone-manage db_sync

# Check migration status
kubectl exec -n openstack keystone-api-xxx -- \
  keystone-manage db_version
```

#### Issue: API Endpoints Not Responding

**Symptoms:**
```bash
openstack endpoint list
# Connection timeout or 503 errors
```

**Causes:**
- Service pods not ready
- Ingress/load balancer issues
- Certificate problems

**Solutions:**
```bash
# Check service status
kubectl get svc -n openstack

# Check ingress
kubectl get ingress -n openstack

# Check pod logs
kubectl logs -n openstack -l application=keystone --tail=50

# Test internal connectivity
kubectl run -it --rm debug --image=curlimages/curl --restart=Never -- \
  curl http://keystone-api.openstack.svc.cluster.local:5000

# Check certificates
kubectl get certificates -n openstack
```

#### Issue: Nova Compute Services Down

**Symptoms:**
```bash
openstack compute service list
# Shows compute services as down
```

**Causes:**
- Nova conductor not running
- RabbitMQ connection issues
- Libvirt connectivity problems

**Solutions:**
```bash
# Check nova-conductor
kubectl get pods -n openstack -l application=nova,component=conductor

# Check RabbitMQ connectivity
kubectl exec -n openstack nova-conductor-xxx -- \
  rabbitmqctl list_connections

# Restart nova-compute on compute nodes
kubectl delete pod -n openstack -l application=nova,component=compute

# Check libvirt
kubectl exec -n openstack nova-compute-xxx -- \
  virsh list --all
```

#### Issue: Neutron Agents Not Alive

**Symptoms:**
```bash
openstack network agent list
# Shows agents with alive=False
```

**Causes:**
- OVN/OVS connectivity issues
- Agent configuration problems
- RabbitMQ connection issues

**Solutions:**
```bash
# Check neutron-server
kubectl get pods -n openstack -l application=neutron,component=server

# Check OVN status
kubectl exec -n openstack neutron-ovn-metadata-agent-xxx -- \
  ovn-nbctl show

# Restart agents
kubectl delete pod -n openstack -l application=neutron

# Check agent configuration
kubectl logs -n openstack neutron-ovn-metadata-agent-xxx
```

#### Issue: Helm Upgrade Timeout

**Symptoms:**
```bash
helm upgrade --install <service> ...
# Error: timed out waiting for the condition
```

**Causes:**
- Slow image pulls
- Resource constraints
- Readiness probe failures

**Solutions:**
```bash
# Increase timeout
helm upgrade --install <service> ... --timeout 20m

# Check image pull status
kubectl get pods -n openstack -o jsonpath='{.items[*].status.containerStatuses[*].state}'

# Check readiness probes
kubectl describe pod <pod-name> -n openstack

# Temporarily disable readiness probes (not recommended for production)
# Edit deployment and comment out readiness probe
```

## Post-Upgrade Tasks

After successful upgrade:

1. **Update Documentation:**
   - Document any custom changes made during upgrade
   - Update runbooks with new procedures
   - Record upgrade duration and issues encountered

2. **Monitor Performance:**
   - Monitor API response times
   - Check resource utilization
   - Review error rates in logs
   - Set up alerts for anomalies

3. **User Communication:**
   - Notify users that upgrade is complete
   - Document any changes in behavior
   - Provide updated documentation links

4. **Cleanup:**
   - Remove old backups after verification period (30 days recommended)
   - Clean up old helm releases
   - Remove temporary resources

5. **Security Review:**
   - Review security advisories for Epoxy
   - Update security policies if needed
   - Rotate credentials if required
